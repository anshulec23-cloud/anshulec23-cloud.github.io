Aegis ICS

A zero-trust gateway that sits inline between industrial field devices and the control network — validating every frame, testing every setpoint against physical stability limits, and cutting power to a relay when a command would push the process somewhere it cannot come back from.

The problem

A conventional industrial IDS sniffs network traffic and raises an alert. By the time anyone reads it, the command has already reached the actuator. Physical processes do not wait for a SOC queue.

Four failure modes drove the design:

  • Coordinated multi-variable stress. A setpoint that is harmless on its own threshold alarm can destroy equipment when combined with another variable's current state — raising temperature while pressure is already elevated. Single-variable alarms are structurally blind to this.
  • Field device hijacking and replay. Industrial fieldbuses are usually unauthenticated. Anyone with bus access can inject forged telemetry or setpoints.
  • Telemetry staleness. When sensors drop out, traditional interlocks tend to fail open — they skip the cross-variable check rather than refusing the command.
  • Uncontained cascades. A compromised node stays on the control network while someone decides what to do about it.

Zero-trust by default

Every sensor frame is checked three ways before it is allowed to influence anything: schema structure, timestamp freshness under 120 seconds, and a FIPS 198-1 HMAC-SHA256 signature over a canonical serialisation. A frame that fails any check is dropped, and a setpoint arriving without fresh telemetry behind it is refused rather than waved through. Fail-closed, not fail-open.

Keys nobody has to provision

New ESP32 slaves announce themselves on the bus and the operator approves each one with a click. Session keys are derived per device with X25519 and HKDF-SHA256 — no shared secret, no pre-provisioned key material, and one firmware image for every node because device IDs are derived from the MAC. Boot and sequence numbers in each frame make replay detectable.

The part worth arguing about

The machine-learning classifier does not decide whether to quarantine a device. Deterministic rules and the trust score do that. The Random Forest only names the attack — fdi_spike, stuxnet, thermal_drift, sensor_fault, normal — and hands that label, with its confidence and the matching MITRE ATT&CK for ICS technique, to the reporting and financial layers.

That split is deliberate. A model that goes quiet, drifts, or is adversarially nudged cannot weaken the defensive response, because the response was never conditional on it. The ML makes the incident legible; the rules make it safe.

Beyond detection

Each approved device carries a financial profile. When an incident is live, the loss engine computes actual loss, projected loss if left unfixed, the catastrophe avoided, time-to-fix and restabilisation cost, expressed through FAIR and regulatory exposure. A one-click report maps the whole thing onto NIST SP 800 controls with ML-selected mitigations and recovery times.

Operator actions — logins, setpoint changes, rule edits — are logged against the verified 3D spatial coordinates of the terminal they came from, so an insider action has a location attached to it and not just a username.

A localhost-only, token-authenticated red-team backend drives a staged eight-attack campaign against the running system so the defence and the loss numbers can be exercised rather than asserted.

Honest limits

Scope

The portable USB attack-drill runner is distributed separately and is not in this repository. Where the README and docs/ disagree, docs/ reflects the actual code — it is the authoritative reference.

The physical enforcement path has been exercised on an ESP32 testbench with simulated process dynamics, not on a production plant. The stability manifolds encode a model of the process; a model that is wrong about the physics will be confidently wrong about safety, which is why the deterministic invariants sit alongside it rather than behind it.
