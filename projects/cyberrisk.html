CyberRisk Platform

Detection is the easy half. This takes an industrial attack and answers the question the people who fund security actually ask: what does this cost us? — in downtime, SLA penalties and regulatory exposure, while the incident is still running.

Domain
OT risk quantification
Pipeline
5-agent LangGraph DAG
Stack
LangGraph, FastAPI, MQTT, React
Reporting
NIST SP 800-61

The problem

A bank, insurer or lender with exposure to an industrial asset has no good way to turn "the refinery's control network was compromised" into a number. The security tooling speaks in severities and CVEs; the credit committee speaks in currency. Nothing bridges the two while it still matters.

This is a cyber incident risk engine with a financial layer on top — explicitly not an investment-risk tool. It answers what a given incident on a given asset is likely to cost, and flags the credit consequence.

How it works

MQTT telemetry (ICS devices / simulator via Mosquitto)
      |
      v
+-------------------- LangGraph DAG --------------------+
| [1] Detector       Random Forest anomaly score (0.65+) |
| [2] Classifier     attack type, severity, confidence   |
| [3] Isolator       micro-segmentation decision         |
| [4] RiskQuantifier financial blast radius              |
| [5] Reporter       NIST + credit risk assessment       |
+--------------------------+----------------------------+
             |             |              |
             v             v              v
         FastAPI      SQLite / PG     WebSocket
          REST                        live dashboard

Why a graph and not a function

Each stage is an agent with one job and an explicit contract with the next. Staging it as a DAG rather than a single procedure means a stage can be swapped, re-run or inspected on its own, and the state at every hop is a readable object rather than a local variable buried in a call stack. When an incident report is later disputed, the chain that produced it can be walked backwards.

Isolation is an action, not a recommendation

The Isolator does not file a ticket. It publishes micro-segmentation commands over MQTT and cuts the device off. Containment that waits on a human has already lost the time that mattered.

What the output looks like

{
  "attack_type": "PhysicalTamper",
  "severity": "critical",
  "device_type": "oil_refinery",
  "anomaly_score": 0.91,
  "estimated_downtime_h": 24,
  "downtime_cost_usd": 19200000,
  "sla_penalty_usd": 2880000,
  "regulatory_fine_usd": 1500000,
  "total_exposure_usd": 23580000,
  "credit_risk_flag": "CRITICAL"
}

Downtime, SLA and regulatory components are kept separate rather than rolled into a single headline figure, because they have different confidence levels and a reader needs to be able to discount them independently.

Honest limits

Where the numbers come from

The financial model is only as good as its per-device cost parameters, which are entered, not learned. Hourly downtime cost, SLA terms and regulatory regime are inputs supplied by whoever configures the asset — the engine does arithmetic on them faithfully and has no way to know when they are optimistic.

The example above is a worked output, not a validated prediction. Treating a figure like that as a forecast rather than a parameterised estimate is the failure mode this kind of tool invites, and the reason the components are reported separately.
